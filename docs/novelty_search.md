# Novelty search: third-party FT8 exchange analysis and a QGIS ham-radio plugin

Search date: 2026-11-11. Method: web searches (general, GitHub, PyPI, HamSCI, arXiv, TAPR, QGIS plugin repository), with sources read directly where possible.
Tags: **[verified]** = I read the primary source. **[secondary]** = seen only in snippets or summaries. **[unverified]** = could not open it.

## TL;DR verdicts

| # | Technique | Verdict |
|---|---|---|
| 1 | Rebuilding third-party FT8/FT4 QSOs from your own decodes and mapping them as lines | **Done before** (the rebuilding and the lines). **Likely new**: pulling out both exchanged reports plus the observer's own SNR as a structured "SNR triangle" per exchange. |
| 2 | "What I see vs what they see": the intended receiver's report compared with the observer's decode SNR, as a median per station | **Partially done.** Related ideas compare receivers on the same signal, or compare your own sent and received reports. Using the report inside an overheard message as the reference receiver is likely new. |
| 3 | Network least-squares "station balance" from the report difference in each two-way exchange | **Likely new** as a network or third-party generalisation. The single-station form is known (DK3BA 2024, KK5JY "mean differential"). |
| 4 | QGIS plugin with PSK Reporter, live WSJT-X, ionosphere checks and Es detection | **Partially done.** One QGIS ham plugin exists (HamQ, with live WSJT-X and an ADIF map), but it has no propagation, spot or ionosphere features. I found no ArcGIS equivalent. The combination is new. |

## Closest prior art per item

1. **ft8decoder (2025)** and **GridTracker QSX Q-paths.** Rebuilding a third-party exchange from CQ to 73 out of the UDP feed and drawing lines is not new. What remains new: (a) building the exchange from ALL.TXT as well as live UDP; (b) explicitly extracting the two exchanged reports (A heard by B, B heard by A) and the observer's decode SNR of each side as a three-receiver SNR "triangle"; (c) treating these as analysable GIS features.
2. **73QRZ RX head-to-head**, **wsjt_all / ALLPLOT / WsjtxUtils.Compare**, and **DK3BA/KK5JY.** All of them compare SNRs of the same signal at two receivers, but the second receiver is either your own second rig or another PSK Reporter spotter. I found nothing that uses the *report embedded in an overheard message* as the second receiver's measurement, with a median per station.
3. **DK3BA 2024** (and **KK5JY 2023**). Both average Rcvd minus Sent over *their own* QSOs, which amounts to a star graph centred on the operator. I found no extension to a graph of third-party exchanges, and no least-squares or graph-Laplacian solve giving station offsets up to a constant. The estimator is mathematically standard (the same as levelling networks in geodesy, or pairwise-comparison ranking), so the claim should be "application", not "new mathematics".
4. **HamQ** is the only ham-radio QGIS plugin found. It covers logging and maps, not propagation. Es detection from FT8 midpoints and KC2G MUF maps exist separately. I found no ArcGIS add-in.

## Suggested honest novelty wording

- Item 1: "Building on the QSO-tracking idea in tools such as GridTracker (QSX paths) and ft8decoder, we extract from each overheard exchange both reports the stations sent each other plus our own SNR for each side, giving three independent receiver measurements per exchange, and map them as great-circle features in QGIS. We are not aware of earlier work that analyses this SNR triangle."
- Item 2: "Unlike A/B receiver comparisons (wsjt_all, ALLPLOT) or PSK Reporter head-to-head comparisons, we use the report that the intended receiver itself transmitted as the reference measurement…"
- Item 3: "DK3BA (2024) and KK5JY (2023) showed that averaging Sent minus Received over one's own QSOs cancels path loss and antenna gain. We generalise this to all decoded two-way exchanges and solve the resulting network by least squares, which gives relative station offsets up to an additive constant. To our knowledge this network form has not been published for amateur radio." Avoid "first" or "novel" without qualification. Say "to our knowledge, based on a search of X, Y, Z".
- Item 4: "HamQ provides logging and Maidenhead tools in QGIS. This plugin adds propagation-oriented layers…"

## Gaps in the search

- **Magazines not indexed:** I could not search the full text of QST, QEX, RadCom, DUBUS or CQ. ARRL periodicals and the RSGB archive are members-only. A "signal report" study, especially around the "Technical Correspondence" / "Technical Topics" columns, could exist there.
- **groups.io (WSJT-X, FT8-Digital-Mode, GridTracker)** blocked automated fetching (HTTP 402). Threads were seen only as titles. Search these manually for "reciprocal", "both reports" and "QSX".
- HamSCI proceedings 2018–2026 were checked only through web search, not by browsing each year's abstract book. The TAPR DCC proceedings were likewise checked only through search. The 2020 HamSCI abstracts PDF was not read in full.
- Source code was not read for M0LTE wsjtx-all-scanner, ft8-qso-log or ALLPLOT. GridTracker's source was not checked for report pairing. JTAlert, JTDX and MSHV feature lists were not checked in detail.
- I did not search Japanese, German or Russian-language forums. DK3BA also has German versions of his papers.
- WSPR has no QSO reports, but WSPR "reciprocal pair" studies (A→B vs B→A spots) could support an analogous network method. Only a light search was done here (Gerzoff's earlier work is [unverified]).
